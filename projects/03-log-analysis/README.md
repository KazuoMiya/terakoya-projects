# 課題3: ログ解析・障害検知ツール

障害対応の朝、あなたは大量のログから「いつから・何が・どれくらい」を、grep と
目視で掘り出している。その調査を、**誰がやっても同じ結果になる道具**にする。
ログを集計し、エラーの**急増**を見つけ、レポートにまとめ、異常のときだけ知らせる。

> この README が課題の「正」だ。コース本文（レッスン proj-13〜15）は、この仕様の
> 読み解きと道しるべ。迷ったら、ここに書いてある完了条件へ戻ってくればいい。

## 検証用のログ（答えが決まっている）

`logs/app.log` に2日分のアプリケーションログが入っている。このログには
**答えが仕込んである**。2026-07-15 の 14時台に、DB接続タイムアウトの急増（44件）だ。
ふだんの ERROR は2〜4件/時。あなたのツールは、この差を自力で見つける。

スタックトレースの続きなど、**形式に合わない行もわざと混ぜてある**。
本物のログには必ず変な行が混ざる。それで落ちる解析ツールは、道具にならない。

## 作るもの

`src/log_check.py` を、次のことができる CLI に仕上げる。

1. ログを**1行ずつ**読む（全部メモリに載せない——本番のログはGB級になる）
2. 各行を分解する（日時・レベル・メッセージ）。**壊れた行は数えて飛ばす**（落ちない）
3. ERROR を時間帯ごとに集計する
4. **急増（スパイク）を検知する**——それまでの平均 × `--factor` 以上、**かつ**
   `--min-count` 以上。倍率と絶対数の**二段構え**
5. 結果を **Markdown のレポート**にして出す
6. **急増があったときだけ**通知する（Slack Incoming Webhook）。正常時は沈黙
7. 全体の状態に応じた**終了コード**で終わる（急増あり=1／なし=0／ログが読めない=3）

## アラート疲れ——この課題でいちばん大事なこと

倍率だけで急増を判定すると、深夜にエラーが1件→3件になっただけで「3倍増！」と
通知が鳴る。それが毎晩続くと、**人は通知を読まなくなる**。読まれない通知は、
存在しないのと同じだ。本物の障害の通知まで、一緒に無視される。

だからこの課題の急増判定は二段構えにする。

```
件数 >= それまでの平均 × factor   （倍率: いつもと比べて多いか）
かつ
件数 >= min_count                 （絶対数: そもそも騒ぐほどの量か）
```

そして**通知は異常のときだけ**。正常なときに「今日も正常です」と毎日鳴らさない。
沈黙が正常の合図。それが、読まれ続ける通知の作法だ。

## 自動採点が見るところ

自動採点（`tests/test_log_check.py`）がテストするのは、**純関数3つ**。
ファイル読み・レポート・通知は環境に依存するので採点しない（自分で確かめる）。

| 関数 | 役割 |
|---|---|
| `parse_line(line)` | 1行を `{"time", "level", "message"}` に分解。形式外は `None`（落ちない） |
| `bucket_by_hour(records, level="ERROR")` | 時間帯（先頭13文字）ごとの件数を数える |
| `detect_spike(series, factor=3.0, min_count=10)` | 急増した時間帯を返す。**二段構え**・境界は「以上」 |

`worst_status` と `status_to_exit_code` は課題1で自分が書いたものが最初から入っている。

## 通知（Slack が無くても完了できる）

通知先は Slack の **Incoming Webhook**（URLにPOSTするとメッセージが届く仕組み）。

- **Webhook URL は「URLの形をしたパスワード」だ。** 知っていれば誰でもそのチャンネルに
  投稿できる。コードに書かず、`.env` に置く（`cp .env.example .env`）。
- Slack を使える環境が無い人へ: **URL が未設定なら、通知本文を画面に表示するだけでよい**。
  それで完了条件を満たす。作る価値があるのは「異常のときだけ知らせる」という設計のほうだ。
- pip の準備（venv の中で）: `pip install -r requirements.txt`（requests と python-dotenv）

## 進め方（5つのマイルストーン）

各段で「動くもの」を持ちながら進む。1〜3は純関数なので、書くたびに採点の緑が増える。

1. **parse_line を緑に** — 1行を分解できる。壊れた行で None を返せる
2. **bucket_by_hour を緑に** — 時間帯ごとに数えられる
3. **detect_spike を緑に** — 急増を見つけられる。**ここで採点は全部緑になる**
4. **ファイルから一周** — logs/app.log を読んで、見本の数字（解析471行・ERROR163件・急増は14時台だけ）と突き合わせる
5. **通知をつなぐ** — 急増のときだけ Slack へ。正常時は沈黙することも確かめる

## 発展（任意）: 無人で動かす

人が手で実行する道具は、まだ「半分だけ自動化」だ。cron（決まった時刻にコマンドを実行する
Linux の仕組み）に載せると、無人で回る。ここで初めて出会う罠が2つある。

1. **PATH と作業ディレクトリが違う。** cron の中は、あなたのターミナルとは別世界だ。
   `python` ではなく **venv の python を絶対パスで**指定し、ログのパスも絶対パスで書く。
2. **結果の置き場が要る。** 画面が無いのだから、出力はファイルに残す。

```bash
# crontab -e で1行足す例: 毎朝7時に点検してレポートを残す
0 7 * * * /home/you/terakoya-projects/.venv/bin/python /home/you/terakoya-projects/projects/03-log-analysis/src/log_check.py /var/log/app.log >> /home/you/log_check_report.md 2>&1
```

WSL2 は cron のサービスを起動しておく必要がある（`sudo service cron start`）。
数日回して、レポートのファイルに毎朝の結果が追記されていれば成功だ。**やらなくても課題3は修了**。
