# 出力の見本（自己チェック用）

同梱の `logs/app.log` に対して実行したときの見本だ。このログは**答えが決まっている**——
2026-07-15 の 14時台に、DB接続タイムアウトの急増（44件）が仕込んである。
あなたのツールがこれを拾えなければ、どこかがずれている。

レポートの見た目は多少違ってよい。**数字と判定**が合っていることが大事だ。

## 実行例

```
$ python src/log_check.py logs/app.log
```

```
# ログ点検レポート

- 解析した行: 471（読めなかった行: 3）
- 件数: ERROR 163 / WARN 20 / INFO 288

## ⚠ 急増を検知した時間帯

- **2026-07-15 14時台**: ERROR 44 件

| 時間帯 | 件数 |
|---|---|
| 2026-07-15 14 | 44 ⚠ |
| 2026-07-15 23 | 4 |

```

終了コード: `1`（WARNING）。`echo $?` で確認できる。

## 合わせるべき数字

| 何が | いくつ |
|---|---|
| 解析できた行 | **471** |
| 読めなかった行（空行は数えない） | **3** |
| ERROR の総数 | **163** |
| 急増と判定される時間帯 | **2026-07-15 14 だけ**（44件） |
| 終了コード | **1**（急増あり＝WARNING） |

- 急増が **1つだけ** 検知されることが大事だ。2026-07-15 23時台（4件）や
  深夜の3件などで鳴っていたら、min_count のガードが効いていない。
- 逆に何も検知されなければ、factor か比較の向き（`>=`）を疑う。

## 通知の確認

- `SLACK_WEBHOOK_URL` を設定していない場合: 「通知先が未設定なので表示のみ」の
  ような表示で通知本文が確認できれば良い（**Slack が無くても課題は完了できる**）。
- 設定した場合: 急増のときだけ届く。**正常なログで実行したときに何も届かない**ことも
  確かめる（正常時は沈黙——それが通知の作法だ）。

## 自己チェックの観点

- [ ] 解析行数・読めなかった行数・ERROR総数が上の表と一致
- [ ] 急増が 2026-07-15 14時台 **だけ** 検知される
- [ ] 壊れた行（スタックトレース等）で例外にならず、数えて飛ばしている
- [ ] 終了コードが判定と一致（急増あり=1／なし=0／ログが読めない=3）
- [ ] 正常時（急増なし）には通知が飛ばない
