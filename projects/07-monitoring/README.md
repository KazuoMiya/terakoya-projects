## 全体の形

```
config.json ──→ monitor.py ──(interval_seconds ごとに)──→ 各対象をチェック
                    │                                        │
                    │  状態が変わったときだけ警告ログ          │ 結果（毎回）
                    ▼                                        ▼
              journalctl / 画面                 課題5のAPI（:8000）→ DBに履歴
```

監視対象は2種類。**http**（URLを叩いて応答コードと時間を見る）と、
**disk**（ディスク使用率。課題2の `shutil.disk_usage` の再利用）だ。

大事な設計が1つある。**監視の経路と、記録の経路を分ける。**
http の監視対象は Nginx 経由の `http://localhost/health`（玄関）、
記録の送り先は `http://127.0.0.1:8000`（奥のAPIに直接）。
だから玄関（Nginx）が死んでも、その異常を奥のDBに記録できる。
「対象の障害」と「監視自身の障害」を区別する仕組みが、経路の分け方に表れている。

## 作るもの

`src/monitor.py` を、次のことができるツールに仕上げる。

1. `config.json` を読み、**起動する前に**検証する（おかしければ分かりやすい言葉で止まる）
2. `interval_seconds` ごとに、全対象をチェックする
3. 結果を**毎回**、課題5のAPIに POST する（履歴がDBに貯まる）
4. **状態が変わったときだけ**警告ログを出す（悪化も、回復も。同じ状態では黙る）
5. 1対象の失敗で全体を止めない
6. **記録に失敗しても監視は止めない**（ログに残して次の周回へ）
7. `--once` で1周だけ実行できる（テストとデモに使う）

## 非機能要件は、この3つだけ

「非機能要件」という言葉に身構えなくていい。この課題では次の3つを指す。

1. **部分障害でも続行する** — 1対象の失敗・記録の失敗で、監視全体を止めない
2. **監視自身のログを残す** — 監視が何をしたか・何に失敗したかを、あとから追える
3. **しきい値は設定ファイルに** — コードを書き換えずに、閾値と対象を変えられる

**やらないこと**（現場では要るが、この課題の外）: 多台数への拡張、冗長化（HA）、
通知チャンネルの拡充、暗号化、Web画面。対象は2つで十分。ループは逐次で十分。

## 自動採点が見るところ

自動採点（23件）が見るのは**純関数3つ**。ループとHTTPは環境で変わるので、
デモシナリオで自分で確かめる。

| 関数 | 役割 |
|---|---|
| `parse_config(config)` | 設定の検証。起動する前に、分かりやすい言葉で止める |
| `judge_http(status_code, elapsed_ms, warn_ms, crit_ms)` | 繋がらない・200以外は CRITICAL。あとは応答時間で判定 |
| `should_alert(prev_status, curr_status)` | 状態が**変わったときだけ** True。アラート疲れの最終試験 |

`worst_status` と `status_to_exit_code` は課題1の成果として最初から入っている。

## 合格条件 — デモシナリオ1本

このシステムの合格は、チェックリストの数ではなく**1本のシナリオが通ること**だ。

```bash
# 0. 監視を回しておく（別ターミナル。学習中は interval を 10 秒くらいに）
python src/monitor.py --config config.json

# 1. 玄関（Nginx）を止める ＝ 監視対象の障害を起こす
sudo systemctl stop nginx

# 2. 次の周回で: 警告ログに「web-gate が CRITICAL になった」が1回だけ出る。
#    その異常が、奥のAPI（:8000）のDBに記録されている:
curl -s http://127.0.0.1:8000/servers          # web-gate の id を確認
curl -s "http://127.0.0.1:8000/servers/<id>/checks?limit=3"   # CRITICAL が記録されている

# 3. CRITICAL のまま数周回、警告が「言い続けられていない」ことを確認する（重要）

# 4. 復旧させる
sudo systemctl start nginx

# 5. 次の周回で: 「web-gate が OK になった」（回復）が1回だけ出る。
#    履歴には CRITICAL の期間と回復が残っている
```

これが通れば、あなたは**障害を、検知して、記録して、回復まで見届けた**。
おまけの実験として、途中で `sudo systemctl stop terakoya-api`（記録先を止める）も
試してほしい。監視は落ちずに「記録できなかった（監視は続ける）」と言い続け、
APIを戻せば記録が再開する。監視自身の障害に、監視が耐える瞬間だ。
