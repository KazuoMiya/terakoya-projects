# 課題4: 構成情報の収集と差分検知

「気づいたら設定が変わっていた」をなくす道具を作る。
サーバーの構成（パッケージ・サービス・ポート・ユーザー・cron）をJSONに書き出し、
前回のスナップショットと比べて、**変わったところだけ**を報告する。

> この README が課題の「正」だ。コース本文（レッスン proj-16〜18）は、この仕様の
> 読み解きと道しるべ。迷ったら、ここに書いてある完了条件へ戻ってくればいい。

**環境構築は要らない。** DockerもDBも立てない。差分エンジンは同梱のサンプル2枚で作り、
仕上げに自分のマシン（WSL2/Ubuntu推奨）の本物の構成で動かす。

## この課題の心臓 — 「差分ゼロが正常」

構成差分ツールの敵は、検知漏れではなく**ノイズ**だ。
収集時刻のような「揺れて当然の値」を差分に混ぜると、毎日レポートが差分だらけになり、
3日で誰も読まなくなる（課題3のアラート疲れの、レポート版だ）。

だから順序が決まっている。**まず「差分ゼロ」が出る状態を作る。**
揺れる値は比較の前に落とす（`normalize`）。同じマシンで2回続けて実行したら
「差分なし」と言える——それがベースライン（比較の土台）であり、
その静けさがあって初めて、本物の変化が浮かび上がる。

## 作るもの

`src/config_diff.py` を、次のことができる CLI に仕上げる。

1. 構成情報を**OSコマンド経由で**集めてJSONに書き出す（収集時刻も記録する）
2. 揺れる値を落とし、順序を揃える（`normalize`）
3. 前回のスナップショットと比べ、**増えた・減った・変わった**を出す（`diff_config`）
4. リストは丸ごとでなく**中身**で比べる（「packagesが変わった」ではなく
   「openssl のこの版が増え、この版が減った」と言えるのが、使えるレポートだ）
5. 差分ゼロなら OK(0)、差分があれば WARNING(1)、スナップショットが読めなければ UNKNOWN(3)
6. 初回（前回が無い）はベースラインを保存して OK で終わる
7. 収集できない項目があっても落ちず、「取れなかった」と記録して続行する

**なぜ WARNING 止まりか。** 差分は「変わった」という事実の検知であって、
それが正しい変更か事故かはツールには分からない。判断するのは人間だ
（課題2の鉄則「検知と対処を分ける」と同じ思想）。

## 収集する項目（Ubuntu / WSL2 前提）

| 項目 | 取り方のヒント |
|---|---|
| パッケージと版 | `dpkg-query -W`（"名前 バージョン" の一覧に整形する） |
| 動いているサービス | `systemctl list-units --type=service --state=running` |
| 待ち受けポート | `ss -tlnH`（4列目 `0.0.0.0:80` の末尾がポート番号） |
| ログインできるユーザー | `/etc/passwd` を読む（シェルが `/bin/bash` 等の行だけ） |
| cron | `crontab -l`（**空だと終了コード1が返る。空は異常ではない**——ここを潰すと課題1の「収集失敗」と同じ穴に落ちる） |

Macの人へ: 上のコマンドの多くはMacに無い。**差分エンジン（採点対象）はサンプル2枚で完成できる**ので、
収集はWSL2/Ubuntuの環境がある人の仕上げとする。取れない項目が「取れなかった」と記録されて
ツールが落ちないこと——それ自体が完了条件の一つだ。

## サンプルには物語が仕込んである

`samples/baseline.json`（昨日）と `samples/current.json`（今日）は、同じサーバーの2日分だ。
正しく作った差分エンジンは、**ちょうど5つの変化**を見つける。

1. `openssl` の版が上がった（3.0.13 → 3.0.15）——正当なパッチ適用の顔
2. `nginx` が **services_running から消えた**——パッケージはまだ在る。**「入れてある」と「動いている」は別物**
3. ポート **8080** が新しく開いた——誰が何のために？
4. ユーザー **tempuser** が増えた——作業用？消し忘れ？
5. cron に **`@reboot /tmp/.cache/update.sh`** が増えた——/tmp から再起動のたびに実行される謎のスクリプト。
   **これは不審な変更の典型的な顔だ**（インフラ基礎のセキュリティ章を思い出してほしい）

そして `collected_at`（収集時刻）は両方のファイルで違うが、**差分に出てはいけない**。
それが normalize の仕事だ。

## 自動採点が見るところ

自動採点（21件）が見るのは**純関数4つ**。収集は環境で変わるので採点しない。

| 関数 | 役割 |
|---|---|
| `normalize(snapshot)` | 揺れる値を落とし、リストをソート。**元の辞書は変更しない** |
| `diff_config(prev, curr)` | added / removed / changed。リストは中身で比べる |
| `judge_diff(diff)` | 差分ゼロ→OK、何かあれば→WARNING |
| `select_old_files(entries, days, now_epoch)` | 【発展用】days日以上前のパスを**選ぶだけ。消さない** |

`worst_status` と `status_to_exit_code` は課題1の成果として最初から入っている。

採点には samples/ の2枚を使う**一周テスト**も含まれる——あなたのエンジンが
上の「5つの変化」を全部見つけ、`collected_at` を差分に出さないことを機械が確かめる。

## 発展: dry-run 既定の掃除ツール（このコース初の「変更系」）

ここまでの課題1〜4は、ぜんぶ**読むだけ**のツールだった。現場で本当に怖い（＝価値が高い）のは
**変更する**ツールだ。古いログを消す小さな掃除ツールで、変更系の作法を体に入れる。

作るもの: `src/cleanup.py`。指定フォルダから「days日以上前のファイル」を選んで消す。ただし——

1. **既定は dry-run（予行演習）**。実行しても**一覧を表示するだけで、何も消さない**
2. 本当に消すのは `--execute` を付けたときだけ。消す前に対象一覧を出し、消した結果をログに残す
3. 「選ぶ」は採点済みの `select_old_files` を使う（選ぶと消すを分けたのは、このためだ）
4. **冪等**にする——2回続けて実行しても、2回目は「消すものなし」で正常終了する
5. 対象は自分で作った練習用フォルダだけに向ける（`mkdir /tmp/cleanup-practice` して
   `touch` で古いファイルを作る。`touch -d "40 days ago" /tmp/cleanup-practice/old.log`）

**鉄則: 消す前に見せる。既定では消さない。消したら記録する。**
本物の削除ツールを本物のログフォルダに向けるのは、このコースの外の話だ——
向けるなら、バックアップ（インフラ基礎の回）と許可が先に来る。
